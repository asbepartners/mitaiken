# 利用規約・プライバシーポリシー 同意管理方針

## 目的

「わたしのはじめて帖」における利用規約・プライバシーポリシーのバージョン管理、同意履歴、再同意、運用手順を定める。

この文書は、実装方法だけでなく「なぜこの設計にしたか」を将来確認できるようにするための内部運用文書である。

## 基本方針

- 利用規約とプライバシーポリシーは、ユーザーには1つの同意操作でセットとして同意してもらう。
- 文書のバージョンは利用規約・プライバシーポリシーそれぞれ別に管理する。
- 公開する文書の組み合わせを `legal_releases` で管理する。
- 文書変更時は、既存ユーザーの再同意が必要かを運営側で判断する。
- 軽微な変更では再同意を求めないことができる。
- 重要な変更では `requires_reconsent = true` の新しいreleaseを作成する。
- 同意履歴は上書きしない。常に履歴を追加する。
- `user_legal_acceptances` は、ユーザー本人が実際に同意操作を行った事実だけを保存する。
- 再同意不要のreleaseについて、ユーザーごとの「同意不要」レコードや自動同意レコードは作成しない。
- 最新releaseへの同意履歴が存在しないことは、必ずしも欠損ではない。最後の明示同意以降に未対応の `requires_reconsent = true` releaseがあるかで利用可否を判断する。
- 公開済みの文書versionおよび過去のreleaseを、後から別内容に書き換えない。
- 同意日時はクライアントから受け取らずDB時刻で記録する。
- 同意ユーザーはクライアントから指定させず、認証済みの `auth.uid()` を使用する。

## DBの役割

### legal_documents

公開した利用規約・プライバシーポリシーの各バージョンを管理する。

主な情報:

- `document_type`: `terms` / `privacy`
- `version`: 文書バージョン
- `effective_at`: 適用開始日時
- `path`: 公開ページ

初期versionは `2026-08-29` とする。

### legal_releases

その時点で公開される「利用規約 + プライバシーポリシー」の組み合わせを管理する。

- `terms_document_id`
- `privacy_document_id`
- `release_no`
- `requires_reconsent`
- `effective_at`

文書のどちらか一方だけを変更した場合でも、新しいreleaseを作る。

### user_legal_acceptances

ユーザーがどのreleaseにいつ同意したかを履歴として保存する。

- `user_id`
- `legal_release_id`
- `accepted_at`

既存履歴のUPDATEは行わない。

アカウント削除時は、`profiles` からのcascadeにより当該ユーザーの同意履歴も削除する。

## 新規登録時の考え方

新規登録の流れ:

1. メールアドレスを入力する。
2. 利用規約・プライバシーポリシーを確認する。
3. 「利用規約とプライバシーポリシーに同意します」にチェックする。
4. 確認コードを送信する。
5. ユーザーが6桁の確認コードを入力する。
6. OTP認証に成功する。
7. 認証済みユーザーとして現在のlegal releaseへの同意履歴をDBに保存する。
8. 同意状態を確認できたら通常利用を開始する。

チェックボックスを選択しただけ、または確認コードを送信しただけでは、確定した同意履歴として扱わない。

OTP認証成功後に初めて、認証済み `user_id` と同意履歴を結び付ける。

## OTP認証成功後に同意保存が失敗した場合

Supabase AuthのOTP認証と、アプリDBの同意履歴保存は1つのDBトランザクションにはできない。

そのため、次の状態が一時的に発生する可能性がある。

- Auth認証: 成功
- 同意履歴: 未保存

この状態を専用の「登録失敗」状態として管理しない。

アプリ起動時・ログイン時に同意状態を確認し、必要な同意履歴がなければ通常利用へ進ませず、共通の同意画面を表示する。

これにより、ネットワーク障害等による同意保存失敗と、規約改定後の再同意を同じ仕組みで安全に回復できる。

`registration_completed` 等の重複した状態フラグは原則として持たない。

## 同意画面の表示

### 同意履歴がない場合

理由を推測せず、共通メッセージを表示する。

> はじめて帖をご利用いただくには、利用規約とプライバシーポリシーへの同意が必要です。  
> 内容をご確認のうえ、同意して続けてください。

### 過去の同意履歴があり、その後に再同意必須の変更がある場合

変更理由を確実に判定できるため、次の補足を表示する。

> 利用規約・プライバシーポリシーの更新に伴い、あらためて同意をお願いしています。

### 同意保存時に通信エラー等が発生した場合

> 同意内容を保存できませんでした。  
> 通信状況をご確認のうえ、もう一度お試しください。

OTP認証が成功済みの場合、同意保存の再試行のためだけにOTPを再送しない。

## 再同意判定

新規ユーザーは、登録時点で公開されている最新のreleaseに同意する。

既存ユーザーについては、最後に同意したreleaseより後に `requires_reconsent = true` のreleaseが存在する場合に再同意を求める。

再同意時は、その時点で公開されている最新releaseに同意する。

例:

- release 1: 初期版 / 同意済み
- release 2: 軽微な変更 / 再同意不要
- release 3: 重要な変更 / 再同意必要
- release 4: 軽微な変更 / 再同意不要

release 1まで同意済みのユーザーには再同意を求める。
そのユーザーが同意操作を行う時点でrelease 4が最新なら、release 4への同意として履歴を保存する。

## 規約・プライバシーポリシー変更時の運用フロー

1. 文書を修正する。
2. 修正内容をレビューする。
3. 対象文書の新しいversionを `legal_documents` に追加する。
4. 利用規約とプライバシーポリシーの新しい組み合わせで `legal_releases` を追加する。
5. 既存ユーザーの再同意が必要か判断する。
6. 必要なら `requires_reconsent = true`、不要なら `false` とする。
7. 公開ページとDBのversion・releaseの対応を確認する。
8. テストユーザーで動作確認する。
9. 公開する。
10. 再同意が必要な場合は、既存ユーザーで再同意画面が表示されることを確認する。
11. 同意後、新しい `user_legal_acceptances` が追加されることを確認する。

## 再同意が必要かの判断

機械的に「文書を変更したら必ず再同意」とはしない。

再同意の要否は変更内容に応じて判断する。

例として、誤字修正、表現整理、連絡先等の軽微な更新は再同意不要と判断できる場合がある。

一方、ユーザーの権利・義務、取得する情報、利用目的、第三者提供、外部サービス利用など、ユーザーの判断に影響する重要な変更では再同意を検討する。

法的判断が必要な変更では、必要に応じて専門家へ確認する。

## 禁止事項・事故防止ルール

- 公開済みversionの内容を別内容へ差し替えない。
- 過去のlegal releaseを書き換えて現在の組み合わせにしない。
- 過去のuser acceptanceをUPDATEして新しい同意に見せない。
- ユーザーの同意日時をクライアント入力値で保存しない。
- クライアント指定のuser_idを信用して同意履歴を作らない。
- `handle_new_user()` だけを根拠に同意履歴を自動作成しない。
- ログイン、アプリ起動、OTP認証成功だけを契機に `record_current_legal_acceptance()` を自動実行しない。
- `record_current_legal_acceptance()` は、規約・プライバシーポリシーを提示し、ユーザーが同意チェックを行い、「同意して続ける」等の明示的な同意操作を行った場合にのみ呼び出す。
- OTP送信だけで同意確定とみなさない。

## 実装上の判定

通常画面を表示する前に、認証済みユーザーのlegal acceptance statusを確認する。

- `accepted`: 通常利用可能
- `no_acceptance`: 共通同意画面を表示
- `legal_update`: 更新理由を添えて再同意画面を表示

同意保存後にstatusを再取得し、`accepted` を確認してから通常画面へ進む。

## テスト項目

- 新規登録でチェックなしでは確認コード送信へ進めない。
- 新規登録でOTP認証成功後、同意履歴が1件作成される。
- 同意保存処理を再実行しても同じreleaseの履歴が重複しない。
- 同意履歴がない認証済みユーザーは同意画面になる。
- 再同意不要releaseだけが追加された場合、既存ユーザーは通常利用できる。
- 再同意必須releaseが追加された場合、既存ユーザーは再同意画面になる。
- 再同意後、過去履歴を残したまま新しい履歴が追加される。
- アカウント削除時、ユーザーの同意履歴も削除される。
- 未認証ユーザーから同意記録RPCを実行できない。
- 他ユーザーの同意履歴を読み取れない。

## 将来のスマホアプリ

PWA/Webと将来のiOS/Androidで同じSupabase Auth、同じuser_id、同じlegal acceptance判定を利用する。

同意証跡は端末内ではなくDBを正とする。

これにより、PWAで登録したユーザーが将来スマホアプリへ移行しても、同じアカウント・同意履歴を利用できる。
